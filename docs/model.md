# 模型说明

这里的Agent只是提出交易的程序。用户意图已经整理为结构化授权，项目不处理自然语言理解，也不判断AI的法律代理资格。

## 从授权到执行

授权检查见 [mandate.py](../src/authorization/mandate.py)。撤销、过期、越权操作、超出单笔硬上限、币种不符和禁止收款方会直接拒绝。所有策略都在决策时和执行前检查这些约束。

M1通过基础检查即自动执行。M2在此基础上使用三个OR条件：金额占比≥0.8、收款方新颖性≥1，或者频率风险≥0.6，任一满足便升级人工确认。

M3使用以下分数，参数见 [config.json](../config.json)：

```text
R = 0.20 A + 0.20 P + 0.25 (1-S) + 0.20 V + 0.15 E
```

|变量|含义|数值方向|
|---|---|---|
|A|交易金额/单笔授权上限，评分时最高截为1|越大风险越高；超过硬上限会先被拒绝|
|P|收款方新颖性|越大风险越高|
|S|任务一致性|越大越安全，因此评分用1-S|
|V|频率风险|越大风险越高|
|E|环境异常|越大风险越高|

这是透明的人工评分方案，没有用合成标签训练权重，也不把该权重称为最优值。

|默认M3分数区间|决策|是否模拟执行|
|---|---|---|
|R < 0.25|AUTO_EXECUTE|是|
|0.25 ≤ R < 0.45|OBSERVE|是，留下监测标记|
|0.45 ≤ R < 0.70|ESCALATE|否，等待人工确认|
|R ≥ 0.70|DENY|否|

例如，一笔220元交易、单笔授权上限1000元，P=0.5、S=0.9、V=0.2、E=0.1，则R=0.224。在其他硬约束均满足且快照未改变时，默认M3会自动执行。这个手算只说明规则怎么工作，不说明该交易在现实中一定安全。

## 为什么还要执行前检查

[runtime.py](../src/authorization/runtime.py)把决策时和执行前的快照分别计算摘要。M3、移除风险模块的消融版本以及M2_full发现摘要不一致便拒绝。M1、M2和移除完整性模块的版本仍会复查硬约束，但不使用完整快照一致性门。

例如，收款方被换成另一个没有明确禁止的对象，可能仍满足硬约束；完整性门用于识别这类变化。演示依赖可信快照和不可绕过的执行入口。SHA256摘要本身不是身份认证、签名或不可抵赖机制。

每次决策记录策略、交易/授权标识、分数、原因、前后摘要、执行状态等字段。审计完整率只检查字段是否齐全，不证明日志防篡改，也不等同于全面合规。

## 设计来源

属性参与授权判定的思路参考[NIST SP 800-162](https://csrc.nist.gov/pubs/sp/800/162/upd2/final)，分级运行时处置参考[MAS SAFR v1.1](https://www.mas.gov.sg/-/media/mas-media-library/development/fintech/ai-safr/safr-v1-1.pdf)，身份与委托边界参考[South等，ICML 2025](https://proceedings.mlr.press/v267/south25a.html)。本项目把这些思路具体化为支付场景的规则和模拟比较，不声称首创动态授权或运行时治理。
